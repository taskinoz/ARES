# TF1 / TFO compatibility evidence

15 November 2026. Phase 2 targets Titanfall Online (TFORevive.Core 135) and
Titanfall 1 (R1Delta 3.0.5). Full compatibility remains open; this checkpoint
covers selected v29 record layouts, authored brush/flat-patch collision and
rigid props. Northstar and Apex/R5 are outside this milestone.

## Changes and checks

- Eight additional v29 record schemas cover water, cubemaps, world lights,
  lightmap headers, probes, prop probe indices, the probe tree and references.
  Checks include finite fields, indices, tree ranges/cycles and SKY/RTL plane
  sizes. These schemas stay separate from v37's different lighting layouts.
- R1Delta now honors `drop_sequential` instead of silently running those drops
  together. Each body is reported under its original index and destroyed before
  the next spawn. A four-barrel native sequence passed.
- Both adapters log final angles and local model bounds. Speed and transformed
  bounds expectations fail when their required data is missing. Old reports
  containing only velocity can still be checked for speed.
- `physics_observations.py --phy FILE.phy` projects a rigid prop's actual
  collision vertices through its recorded pose. `--floor INDEX Z` checks
  support within one unit and linear speed at most 0.1. Multi-solid articulated
  models are rejected. This is sampled flat-plane support, not broad physics
  stability, stacking, friction or buoyancy acceptance.

Native tests used an original authored map with a brush top at z=0 and a flat
patch at z=128. Both runtimes passed the same two rays and four box hulls with
identical event strings. A four-barrel simultaneous run in each runtime passed
speed and coarse support checks; the actual barrel PHY also passes the saved
pose checks. A separate R1Delta sequential run passed.

Both affected crates had rolled onto their sides. Their visual bounds extend

## Remaining acceptance gates

| Area | Current evidence | Required for full support |
| --- | --- | --- |
| v29 records | Selected structural schemas; six reference maps | Remaining layouts and cross-references, including shadow/CSM and physics blobs |
| Collision | Sampled brushes and a flat patch in both runtimes | Curved/transformed/backface cases, masks, real titans/projectiles and triggers |
| Physics | Rigid-prop poses/support in controlled scenes | Repeated stress and retail controls for the historical fall-through issue; stacking and speeds |
| Water | Static heights/material ranges; earlier TFO buoyancy control | Paired buoyancy, water visibility cells, underwater rendering/fog |
| Lighting | Plane lengths, layouts, probes and tree checks | RTL semantics and paired world/character visual parity |
| Assets | Staged barrel dependencies load in R1Delta | Complete materials/models dependency packaging for standalone releases |
| Gameplay | Baseline spawns and intermission camera | Every supported mode, objectives, traversal and navigation |
| Release | Reproducible authored baseline | Authored and converted maps packaged for both runtimes, with human matches |

Passing the current probes does not close these gates. New failures should be
retained with the runtime version, shared checks, map/compiler fingerprints and
the raw events that identify the failure.

## Held-camera and water follow-up (15 November)

Views now remain under a bounded pose hold during capture and record player
origin/eye position. Missing captures, missing/nonfinite poses and origin drift
over one unit fail. TFO only accepts captures successfully made this launch,
so stale PNGs cannot satisfy checks. R1 holds are cancelled on success/failure.

MRVN's new water draw/shader fixes pass 60 compiler cases. A fresh BSP renders
underwater geometry/fog in TFO Core 135 with all three held positions passing.
The same BSP in R1Delta 3.0.5 renders floor/fog underwater but has a black upper
view and missing surface; the above-water camera also drifted 2.606 units and
correctly failed. Material dependencies/renderer differences need isolation.
Reports are local under MRVN `.local/respawn/phase2-water/{tfo-typed,r1-typed}`.
Paired water and general visual acceptance remain open. No assets are committed.

155 format tests, 68 adapter tests and registry validation pass. An initial
full adapter run hit a Northstar local connection abort; a full rerun passed.

## R1 water controls and capture follow-up (15 November)

Explicit material staging is now available in ARES R1Delta with
`--material-files DIR`: only a local materials/ tree of VMT/VTF files is admitted,
with linked paths and other file types rejected before staging. Owned-addon
cleanup removes these dependencies with the map. This is explicit staging,
not automatic dependency discovery or conversion; no game assets are committed.

A local Angel City VPK control supplied both water VMTs, the normal/flow/noise
textures and HDR cubemap. The two VMTs are byte-identical to the TFO copies.
Supplying these files did not repair the missing R1 water surface/black upper
underwater view. Separate above-only surface and translucent shader controls
also failed to repair rendering. These negative controls do not prove material
loading or general renderer parity; retain the unresolved failure.

Camera drift is now addressed: the fresh local R1 game enables cheats and
uses noclip only for capture, after normal ray/hull/drop checks. It toggles
noclip off in cleanup, including capture errors. Three native origins now
match requests exactly (eye z=252, 76, 76), without loosening the one-unit check.
The raw earlier drift failures remain. Capture success is not visual success:
reviewed water screenshots still show the surface/upper-view problem.

Local reports under MRVN `.local/respawn/phase2-water/`:
`r1-material-control`, `r1-toponly-complete`, `r1-cheat-camera`, `r1-translucent`.
The first above-only control attempts lacked the spawn sidecar; they are setup
failures, not renderer evidence. The complete control includes it.

MRVN now provides `tools/respawn/prepare_tf1_water.py` to reproduce the original
rectangular room, explicit reverse-facing underside, wet/dry cell checks,
shared rays/views and compiler/BSP hashes. It emits the spawn sidecar alongside
the BSP; both must travel together. Fresh generation/static checks and all 232
MRVN tool tests pass; all 70 ARES adapter tests and registry validation pass.
Both READMEs now list TF1/R1Delta with the shared TFO v29 compiler target while
keeping runtime acceptance separate. Full Phase 2 compatibility remains open.

The normal ARES CLI also passes on the fresh generated BSP (no wrapper or BSP
patches): `.local/respawn/phase2-water-repro/r1-native/report.json` records both
rays at z=0.03125 and all three exact camera origins with no errors. All three
screenshots were reviewed; the water surface/upper-view failure persists.
